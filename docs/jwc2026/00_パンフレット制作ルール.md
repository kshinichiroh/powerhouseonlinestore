## 1. チーム掲載名

- 誌面に印字するチーム名は **JBA帳票（2026年度チームメンバー一覧表）の登録名を正**とする。
- トーナメント表PDF・共有フォルダ名・ファイル名・当方の台帳表記が異なっていても、JBA登録名を優先する。

### 例外：トーナメント表だけは表記を直さない（2026-09-15 岸さん決定・2026-09-16 理由を確定）

**トーナメント表については、正本データ（JBA登録名）に合わせない。
既にリリース済みであるため、このまま進める。**

該当は**3か所・2つのチーム名**（男子59 ゴッド ドア／女子8 ゴッド ドア／女子32 HyogoForce）。
組合せページとチーム紹介ページで表記が違ったまま1冊に入るが、**意図的である。**

#### 理由（岸さん・2026-09-16）

1. **トーナメント表が既にリリースされていること。** ウェブサイト等で一般に公表済みで、
   いま表記を変えると公表済みのものと誌面が食い違い、かえって混乱を招く。
2. **スペースの有無という軽微な差異であること。** 別チームと誤認される恐れがない。
   （2026-09-16にデータで検算。組合せ127件のうちJBA登録名と異なるのは上記3件のみで、
   **3件とも空白を除けば完全一致**。文字そのものが違う例は1件もない）

#### 適用範囲

| どこ | 何を印字するか |
| --- | --- |
| **組合せページ（トーナメント表）だけ** | **公表済みのトーナメント表PDFの表記のまま** |
| メンバー表・チーム紹介ページ・台帳・その他すべて | **JBA帳票の登録名**（ルール1のとおり。一切崩さない） |

- この例外が及ぶのは**トーナメント表のみ。** 他の資料へ広げない。
- **ダイコロ様には「意図的なので統一しないでください」と明示して伝える。**
  親切心で揃えられてしまうと、公表済みの組合せと食い違う。
  入稿Excelの `07_表記ゆれ` シートにも同じ注記を入れてある。
- この例外を他のチーム・他の資料へ広げない。**新たに表記ゆれが見つかったときは、
  この例外の対象ではなくJBA登録名に直す。**

- 過去に通知済みの訂正例: teamDENY→team DENY、BAY CROWN JUNIOR→BAYCROWN JUNIOR、
  North Wave→NorthWave、WESTRIVER→WEST RIVER。

## 2. チーム紹介ページの構成

- **チーム紹介文は入れない。** 掲載するのは 集合写真（またはロゴ）・チーム名・選手名簿 のみ。
- 各チームの広告枠内にある文言は、その広告デザインの一部としてそのまま掲載する。

## 3. 集合写真がないチーム

- 集合写真の提出は **任意**。写真がないチームは「未提出」ではなく **「写真なしで確定」**。
- ロゴがある場合はロゴを使用。ロゴもない場合はチーム名と名簿のみで組む。
- 素材受付は終了しているため、追加提出は発生しない。催促・再確認は不要。

## 4-2. 同姓の2名を1人にまとめない

**チームには親子・兄弟が普通にいる。同姓であることは同一人物の根拠にならない。**

- 男子32 U14 ゴッドドアの魚住は**母子**（2026-09-15 岸さん）。
  原本で確認した結果、**JBA正本に魚住姓は3名**いた。
  **魚住 夏鈴＝コーチ（母／誌面のHC）／魚住 琉煌＝競技者（子）／魚住 彩希＝チームスタッフ。**
  誌面のスタッフ欄に出るのは夏鈴のみ。**「魚住 愛鈴」という人物は存在せず、OCRの誤読だった。**
  大会申込書とJBA正本でJBAメンバーIDが一致したため同一人物と確定した。
- ゴッドドアは3チーム（男子59 ゴッドドア／男子32 U14 ゴッドドア／女子8 ゴッドドア）あり、
  えびす3チームと同じく家族が別チームに登録されている可能性がある。

判定の手順:

1. 大会申込書とJBA正本それぞれに同姓が**何名いるかを数える**。数が違えば、氏名の一致だけでは対応が決まらない。
2. **JBAメンバーIDが両方に出ていれば、IDの一致・不一致で確定する。** これが最も確実。
   ただし**IDの数字は成果物にも報告にも残さない**（「一致」「不一致」とだけ書く）。
3. 確定できなければ、両方を別行のまま残して `要確認` にする。**推測で1人にまとめない。**

## 7-3. メール下書きの扱い（2026-09-16 追加・事故未遂に基づく）

**下書きは、作った時点の事実のまま固まる。時間が経つと、その記述は嘘になる。**

### 原則：作ったら、その場で送る。送らないなら消す。

持ち越さない。**持ち越した下書きは、次に開いたときには古い。**

やむを得ず残す場合は、**本文の冒頭に次の1行を入れる。**

```
※この下書きは YYYY-MM-DD 時点の内容です。送信前に事実を再確認してください。
```

### 送信直前に必ず確認する4点

1. **完了形で書いた記述が、本当に完了しているか。**
   「格納いたしました」「お渡しいたします」「共有済みです」と書いてあったら、
   **実物を見て確かめる。** 書いた時点では予定でも、送る時点で実行されているとは限らない。
2. **本文中のリンク先が空でないか。** フォルダを案内するなら、中にファイルがあるか開いて見る。
3. **宛先。** 中森様は**3アドレス**（第7-2項）。1つだけになっていないか。
4. **その後に方針が変わっていないか。** 特にスタッフの扱い・表記ルール・番号は動きが速い。

### 実例（2026-09-16 の事故未遂）

2026-09-15 に作った中森様宛の下書きが、翌朝まで残っていた。中身は次のとおり。

| 下書きの記載 | 翌朝の実際 |
| --- | --- |
| 「Excelデータ2点を共有フォルダへ格納いたしました」＋リンク | **格納しておらず、リンク先は空** |
| 「スタッフは未提出。現在TO担当のもとに集約中」 | **9/13-14に受領済みで手元にあった** |
| 「メンバー表には選手のみ。スタッフは含まれていません」 | 当日渡すものは**スタッフ834行入り** |
| 「スタッフ欄を空けた状態で組んでください」 | **不要な依頼**。渡すデータと矛盾する |
| 宛先が `nakamori@daicolo.jp` 1つだけ | 3アドレスにすべきだった |

**送信していれば、空のフォルダを「格納しました」と案内し、手元にあるものを
「集約中」と伝えることになっていた。** 岸さんが送信前に下書きを確認するよう指示されて
発見できた。同じ日に作った他の2件も、送信済みと重複、または失効していた。

## 11-2. 作った素材の保管（2026-09-16 追加・Excel2点消失を受けて）

2026-09-15に生成した入稿用Excel 2点が、翌日には**どこにも存在しなかった。**
Windowsの全ドライブ検索でも0件、Drive側も実査して0件。
再生成そのものは可能だったが、「作ったはずのものが消える」状態を残してはいけない。

### 守ること

1. **生成物は固定パスへ書き出す。** 一時ディレクトリ・使い捨てのgit worktreeの中で作らない。
   worktreeを畳めば中身ごと消える。
2. **生成した直後に、絶対パスとバイト数とSHA-256を記録に書く。**
   この3点が残っていないものは「作った」と数えない。記録に「提出」「生成」とだけ書かない。
3. **リポジトリに置けないファイルは、Driveに二重に持つ。**
   選手・スタッフの個人情報を含む `members_master.csv` `staff_master.csv` は
   `.gitignore` 済みでリポジトリに入らない。**Windows上の1本きりだと、そこが単一障害点になる。**
   非共有フォルダ `JWC2026_大会申込書_原本_非共有`
   （`1bIOVHwb89EFf81E9x9Ha70QgWQHmyKiD`）にバックアップを置く。
   このフォルダはダイコロ様に共有していないため、個人情報を置いてよい。
4. **消えても痛くない状態を作る。** 入稿用Excelは `build_xlsx.py` ＋ 3つの入力
   （`bracket_data.py`／`material_status.csv`／`members_master.csv`）から**再生成できる。**
   照合結果はすべてCSVの中に入っているため、**照合のやり直しは発生しない。**
   守るべきは「検証の成果」ではなく「入力CSV」である。
